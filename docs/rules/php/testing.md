# TDD и PHPUnit

## Цикл изменения

1. **Red.** Записать наблюдаемое ожидаемое поведение тестом и убедиться, что он падает по ожидаемой причине. Для дефекта сначала зафиксировать воспроизводящий его сценарий.
2. **Green.** Сделать минимальное изменение, которое выполняет сценарий.
3. **Refactor.** Упростить реализацию и имена, повторить тесты. Для изменения контракта обновить связанные проверки API и документацию.

Имена тестов описывают условие и результат. Внутри видны подготовка, действие и проверка. Проверяем публичное поведение, сохранённые данные и ошибки. Моки не используем. Для доменных тестов создаём настоящие объекты и передаём фиксированные входы, включая время. Для интеграционных тестов используем настоящие Use Cases, репозитории и PDO SQLite. [Руководство PHPUnit по подготовке тестов](https://docs.phpunit.de/en/12.5/fixtures.html).

## Интеграция с SQLite

- Каждый интеграционный тест получает отдельный временный файл SQLite в контейнере. Используем ту же схему или миграции и те же настройки соединения, что в приложении, включая внешние ключи. Для HTTP-прогона все участвующие процессы используют один файл конкретного теста через `DB_PATH`.
- Подготавливаем минимальные данные, нужные сценарию. Фиксируем время явно. Тесты независимы от порядка запуска и данных демо.
- Закрываем соединения и удаляем временный файл и его вспомогательные файлы после теста, включая падение. Рабочий Compose volume не подключаем к тестовой БД.

## Покрытие

| Уровень | Что проверяем |
|---|---|
| Домен | Инварианты создания и изменения. Каждую пару состояний из согласованной матрицы переходов, границы длины, необязательные значения |
| Use Case и SQLite | Создание, правку и чтение задачи без исполнителя, членство, доступ к архиву и чужому проекту, сохранение комментария с автором, конфликт версии без частичной записи |
| Пограничные условия | Некорректные и отсутствующие поля, разные эффекты отсутствующего значения и `null` в PATCH, срок ровно на границе просрочки и по обе стороны, повторное чтение после записи |

PHPUnit и HTTP smoke запускаем внутри Docker на PHP 8.4. Целевой пример для сервиса инструментов `php-check` из корня проекта:

```bash
docker compose run --rm php-check vendor/bin/phpunit
```

Сервис должен запускаться с рабочим каталогом backend, установленными dev-зависимостями Composer и `pdo_sqlite`. [Архитектура проверок](../../architecture/delivery-and-quality.md).
