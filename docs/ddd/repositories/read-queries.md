# Запросы чтения

Запросы возвращают данные под HTTP-операцию. Они могут объединять таблицы нескольких агрегатов и выбирают только поля, необходимые контракту.

| Операция | Вход и выход | Ограничения и порядок |
|---|---|---|
| Контекст демо | `UserId → Context` | Текущий профиль, каталог демо-пользователей, серверное время UTC и дата инициализации |
| Проекты пользователя | `UserId → list<ProjectSummary>` | Проекты по членству, включая архив, с участниками и счётчиком всех задач. Активные перед архивными, затем по ID |
| Задачи проекта | `ProjectId, UserId → list<TaskSummary>` | Проверить членство. Вернуть все задачи, включая задачи с `assignee_id = null`, по ID. Доступный пустой список отличается от отсутствующего или недоступного проекта |
| Карточка задачи | `TaskId, UserId → TaskDetail?` | Проверить членство в проекте задачи. Вернуть задачу и полное обсуждение с именами авторов. Комментарии идут по ID. Для отсутствующей или недоступной задачи прикладной обработчик возвращает 404 |
| Обзор «Требуют внимания» | `UserId, UtcTimestamp → list<AttentionItem>` | Только активные проекты, где текущий пользователь руководитель и участник. Активная отметка комментария даёт причину `comment_attention` даже завершённой задаче. Для незавершённых задач учитываются `blocked`, `overdue`, `unassigned`. Одна строка на задачу. Сортировка по приоритету причины, затем по сроку и ID |

`AttentionItem` включает ID задачи и проекта, их названия, текущий статус, исполнителя, срок и причины. Для просрочки используется единый момент UTC, переданный на весь расчёт. Полная переписка читается при переходе в карточку. Пустой обзор — успешный результат.

Для v7 достаточно запросов PDO по текущей SQLite. Если список проектов делает отдельную выборку на каждого, при росте объёма можно читать участников пачкой по ID видимых проектов.
