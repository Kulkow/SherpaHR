# План реализации Project Desk v7

Реализованы инфраструктура, доменная модель, контроллеры и текущие Use Cases,
матрица переходов, обзор и отметка комментария. Проверки запускаются по
[правилам разработки](../architecture/delivery-and-quality.md). Границы описаны
в [контексте Project Desk](../ddd/bounded-context.md).

## Шаги

| № | Шаг | Комментарий и результат |
|---:|---|---|
| 1 | Подготовить стартовую архитектуру backend | Сохранить PHP 8.4 без фреймворка, SQLite и Docker. Подключить Composer, автозагрузку, PHPStan и PHPUnit. Определить точку входа API и команды проверок. Снять исходное состояние smoke-теста. [Архитектура](../architecture/implementation.md) |
| 2 | Выделить доменную часть и обеспечить инварианты | Реализовать согласованные сущности и значения. Проверять обязательные поля, допустимый статус, назначение участника проекта и совместимость версий при записи. Членство и архив проверять на границе прикладной операции, поскольку они зависят от проекта. [Доменная модель](../ddd/entity-vo/README.md) |
| 3 | Определить bounded contexts | Описать, где действуют термины и правила и кто владеет данными. Рассмотреть проекты, задачи и обсуждения как один контекст Project Desk, пока у них общий язык и правила доступа. Обзор рассмотреть как модель чтения. По результату зафиксировать границы и согласовать выделенную на шаге 2 модель |
| 4 | Поочерёдно реализовать текущие Use Cases и исправить дефекты | Зафиксировать текущие контракты, затем проверить и перенести UC-01–UC-05 в порядке зависимостей: выбор пользователя, список задач, обсуждение, создание, правка. Исправить пропуск задач без исполнителя и регрессии на границах API. Добавление комментария реализовано вместе с остальными сценариями. [Use Cases](../analyze/use-cases/README.md), [ревью backend](../analyze/backend/README.md) |
| 5 | Организовать frontend по DDD | Сгруппировать Angular-код по пользовательским сценариям и использовать общий словарь. Выделить карточку, список проекта и клиент API с типами из общего контракта. Подключить статанализ, линтинг и тесты. Сохранить существующий путь работы с задачей. [Архитектура frontend](../architecture/implementation.md) |
| 6 | Реализовать текущую задачу и бизнес-процесс статусов задачи | Согласовать начальный статус, матрицу допустимых переходов, условия и полномочия. Проверять переход на сервере по текущему состоянию задачи и версии; UI показывает разрешённые действия. Добавить обзор «Требуют внимания» с объяснением причин и переходом в карточку. Покрыть тестами разрешённые и запрещённые переходы, включая запрос со старой версией |
| 7 | Определить статус внимания у комментария | Согласовать, кто помечает комментарий, кому адресуется отметка, где она видна и как закрывается. Зафиксировать модель состояния и контракт. Состояние внимания к комментарию и рабочий статус задачи описывают разные процессы |
| 8 | Реализовать оставшиеся функции согласованного объёма | Восстановить сохранение комментария с автором и временем, добавить согласованное поведение отметки внимания. Сверить остаток с реестром пробелов. Пройти сквозной сценарий в Docker и подключить тесты и статанализ перед коммитом. [Нереализованное](../analyze/not-implemented/README.md), [проверки и E2E](../architecture/delivery-and-quality.md) |
| 9 | Запросить у автора ответы на оставшиеся вопросы | После получения ограничений по коду вынести на согласование расхождения, влияющие на контракт, бизнес-правила и объём. Ответы фиксировать в документации и критериях приёмки. Вопросы, от которых зависит изменение, согласовывать до этого изменения, сохраняя порядок реализации |

## Согласованные и открытые правила

- [Матрица переходов](../ddd/entity-vo/value-objects.md#переходы-taskstatus) применяется при PATCH. Карточка получает допустимые переходы с сервера. Каждая новая задача создаётся в статусе «Открыта».
- Участник ставит отметку при отправке. Текущий руководитель проекта обрабатывает её из карточки. Активная отметка включает в обзор даже завершённую задачу. Подробности в [UC-06](../ddd/useCase/comments.md).
- В обзоре сначала показываются активные отметки, затем заблокированные, просроченные и неназначенные незавершённые задачи. Это принятое для первой версии правило сортировки.
