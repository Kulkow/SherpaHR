# Backend и frontend

## Backend

PHP 8.4, PDO SQLite и Composer. Composer управляет автозагрузкой PSR-4 и инструментами разработки. PHPStan и PHPUnit указываются в `require-dev`. Версии подбираются под PHP 8.4 и фиксируются в `backend/composer.lock`. Прикладной код использует стандартные возможности PHP и PDO.

| Участок | Ответственность |
|---|---|
| `backend/router.php` | Различить границу `/api` и выдачу собранного frontend. Создать зависимости и передать запрос в обработчик |
| `backend/src/` | Разобрать и проверить HTTP-вход, выполнить операцию, сформировать результат и единообразно обработать ошибки |
| Операции над задачами, обсуждением и обзором | Проверить доступ и правила предметной области. Вынести правила отбора и проверки из маршрутизации по мере роста сценариев |
| Доступ к SQLite | Использовать подготовленные запросы, явные выборки и преобразование строк БД в выходные данные |
| `backend/tests/` | PHPUnit для правил и интеграции с временной SQLite. Существующий HTTP smoke-тест остаётся проверкой API через реальные маршруты |

Достаточно конкретных классов и обычных функций. Отдельный интерфейс появляется, когда существует реальная потребность в нескольких реализациях или в подмене зависимости на границе. Для простых сценариев используем типы PHP и формы массивов PHPStan. Отдельный объект данных имеет смысл, когда он выражает устойчивый контракт или правило.

Инициализацию новой БД выполняем при запуске приложения, проверки версий схемы выполняем по мере её изменения. Обычное чтение и healthcheck обходятся без транзакции записи. При обновлении задачи сохраняем атомарную проверку версии. При ошибке подключения клиент получает JSON API со статусом 500, детали остаются в серверном журнале.

## Frontend

Сохраняем Angular, standalone-компоненты, signals и текущий npm. Разделяем экран обзора, список задач проекта и карточку по мере появления повторного использования. Карточка получает явный контекст проекта задачи, включая состав участников и режим чтения. Состояние загрузки, ошибки и пустого результата хранится отдельно для каждого сценария.

HTTP-клиент предоставляет методы операций с типизированными входами и ответами. Тип черновика формы описывает локальные значения элементов управления. Преобразование в контракт API происходит перед отправкой. При изменении соседних полей сохраняется исходное значение срока с секундами.

Статический анализ включает `tsc --noEmit` и Angular-сборку со `strictTemplates`. Для линтинга предлагаются ESLint, typescript-eslint и Angular ESLint с правилами для TypeScript и шаблонов. Для фронтенд-тестов предлагается Vitest. Версии инструментов выбираются совместимыми с Angular проекта и фиксируются в `frontend/package-lock.json`. Общий глобальный store понадобится, если локального состояния и передачи контекста между компонентами станет недостаточно.
